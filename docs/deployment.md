## 1. Platform choice: Render (Blueprint)

One file, [`render.yaml`](../render.yaml), declares the whole environment:

| Resource | Render type | Built from |
| --- | --- | --- |
| `healthcare-ai-api` | Web service, Docker | `Dockerfile` (FastAPI) |
| `healthcare-ai-frontend` | Web service, Docker | `app/Dockerfile` (Next.js standalone) |
| `healthcare-ai-db` | Managed PostgreSQL | — |

Why Render:

* Runs the two existing Dockerfiles unchanged and provides managed PostgreSQL, so the stack matches `docker-compose.yml` without new infrastructure.
* One declarative file instead of Terraform/AWS (roadmap §8): no VPC, IAM or load balancer to manage.
* Built-in HTTPS, health checks, generated secrets (`generateValue`) and dashboard-managed secrets (`sync: false`).
* A free tier is enough for a demo (see §5).

Redis from `docker-compose.yml` is not deployed: nothing in the application uses it.

## 2. What happens on deploy

The API's start command (`dockerCommand: sh scripts/start_api.sh` in `render.yaml`):

```sh
set -e
python -m db.migrate
python -m db.seed_demo
exec uvicorn api.main:app --host 0.0.0.0 --port "${PORT:-8000}"
```

1. **Migrations** (`db/migrate.py`) apply pending files from `db/migrations/`; applied files are recorded in `schema_migrations`, so this is safe on every start.
2. **Demo seed** (`db/seed_demo.py`) inserts any missing synthetic demo rows (below) and never changes existing ones. It refuses to run (exit 2) unless `APP_ENV=demo`. Since #43 it also seeds eight synthetic intakes with fixed ids (`demo-intake-a1`–`a4` in `default`, `demo-intake-b1`–`b4` in `demo-clinic-b`), one per review status per clinic, processed by the mock pipeline without persistence side effects (no webhook).
3. **Server** starts only if both steps succeed. Render's health check (`GET /health`, which also reports `llm_mode`) only passes once the server is up, so a failed migration leaves the deploy unhealthy instead of serving an unmigrated database.

The migrations run in the start command rather than a pre-deploy command because Render's pre-deploy commands are not available on the free instance type.

The frontend health check is `GET /`.

### Synthetic demo seed

| User id | Email | Clinic | Role |
| --- | --- | --- | --- |

## 3. Environment variables

**API** (`healthcare-ai-api`):

| Variable | Source | Notes |
| --- | --- | --- |
| `DATABASE_URL` | From `healthcare-ai-db` | Internal connection string. |
| `LLM_MODE` | `mock` in `render.yaml` | Real mode requires explicitly setting `LLM_MODE=real` **and** `OPENAI_API_KEY` in the dashboard; startup fails if the key is missing (#22). Not recommended for the public demo. |
| `AUTH_TOKEN_SECRET` | Generated by Render | Signs staff tokens. Needed locally to issue tokens (§6). |
| `WEBHOOK_SECRET` | Generated by Render | Signs webhook payloads. Needed by the receiver to verify signatures. |
| `WEBHOOK_URL` | Dashboard only (`sync: false`) | HTTPS receiver URL. The payload carries only ids ([`escalation_webhook.md`](escalation_webhook.md)). **Unset on the public demo** (§9.1): delivery is then `disabled`. Set it only temporarily, to a receiver you control, for a private webhook check. |
| `CORS_ALLOWED_ORIGINS` | Entered at creation | The frontend's public origin exactly as shown on its service page, e.g. `https://healthcare-ai-frontend-1s23.onrender.com`. |
| `APP_ENV` | `demo` | Shown by `/health`. |

**Frontend** (`healthcare-ai-frontend`):

| Variable | Source | Notes |
| --- | --- | --- |
| `NEXT_PUBLIC_API_BASE_URL` | Entered at creation | The API's public URL. Inlined into the browser bundle at **build** time; it is never a secret. Changing it requires a rebuild. |
| `NEXT_PUBLIC_DEMO_MODE` | `true` (literal, #43) | Browser-visible boolean, inlined at build time. Shows the seeded demo staff identities (user id, clinic, role) on the landing page. Never a credential; tokens are still issued by the operator. |
| `PORT` | `3000` | Next.js standalone server port. |

No secret has a value in the repository. `tests/test_deploy_demo.py` fails if a secret-like key in `render.yaml` has a literal value, if the frontend service receives anything other than `PORT`, `NEXT_PUBLIC_API_BASE_URL` and `NEXT_PUBLIC_DEMO_MODE`, or if the UI reads any other `process.env` variable.

## 4. Deployment steps (requires the account owner)

1. **Receiver (optional).** For a public demo, skip this and leave `WEBHOOK_URL` empty (§9.1). For a private webhook check only, create a receiver URL that shows the raw request body and headers, e.g. a free [webhook.site](https://webhook.site) URL, or any HTTPS endpoint you control. The payload has no PHI.
2. **Render account.** Sign in to Render and connect the GitHub repository.
3. **Blueprint.** Dashboard → *New* → *Blueprint* → select this repository, branch `main`. Render reads `render.yaml` and asks for the `sync: false` values:
   * `WEBHOOK_URL` = receiver URL from step 1, or leave it empty (public demo, §9.1)
   * `CORS_ALLOWED_ORIGINS` = the frontend's public URL
   * `NEXT_PUBLIC_API_BASE_URL` = the API's public URL

   The public hostnames are not known until the services exist: when `<service-name>.onrender.com` is already taken, Render adds a random suffix (this deployment got `healthcare-ai-api-tovn` and `healthcare-ai-frontend-1s23`; the unsuffixed names belong to another account). Enter placeholders if needed, then after creation **copy** each URL from the service page (do not retype it; `l`/`1`/`t` are easy to confuse) and set:
   * API → `CORS_ALLOWED_ORIGINS` → *Save and deploy*;
   * Frontend → `NEXT_PUBLIC_API_BASE_URL` → **Save, rebuild, and deploy**. A plain *Save and deploy* does not rebuild the image, so the browser bundle keeps the old API URL.
4. **Apply.** Confirm the Blueprint with the free plans. `autoDeployTrigger` is `off`, so later deploys are manual (*Manual Deploy* in the dashboard).
5. **Check the API logs** for `Migrations complete` and `Demo seed complete`, and that the service shows as healthy.

## 5. Costs and limitations

All three resources are on Render's **free** plans in `render.yaml` (no payment method should be needed for this configuration; confirm current terms at render.com/pricing before applying). Known free-tier limits, as documented by Render at the time of writing:

* Free web services spin down after ~15 minutes without traffic; the next request waits for a cold start (up to about a minute).
* A free PostgreSQL database expires after a fixed period (30 days at the time of writing) unless upgraded; data is lost. Only one free database per workspace.
* The container filesystem is ephemeral: the JSONL audit file (`audit.jsonl`) is lost on restart. Audit events are also printed to stdout and visible in Render's logs.
* Single instance, single environment, no autoscaling, no backups on the free database.
* Render created the database with PostgreSQL 18, while CI and Docker Compose use PostgreSQL 15. The migrations and seed ran successfully on the hosted database (§7), but the test suite runs only against 15.

Upgrading to paid instance types (roughly a few US dollars per month per service and database) removes the spin-down and expiry; that is a billing decision for the account owner and is not part of this issue.

Other limitations: one webhook receiver for all clinics (none on the public demo, §9.1); tokens are issued by an operator CLI (no login UI); no rate limiting on the public intake endpoint (roadmap §7).

## 6. Hosted verification (exit-criterion flow)

Run from a local checkout with dependencies installed. Values come from the Render dashboard.

```sh
API=https://healthcare-ai-api-tovn.onrender.com   # this deployment; copy yours from the API service page

# 1. Health and mode
curl -fsS "$API/health"          # expect {"status":"ok", ..., "llm_mode":"mock"}

# 2. Issue staff tokens locally against the hosted database.
#    DATABASE_URL = healthcare-ai-db "External Database URL" (dashboard → database → Connect;
#    not the Internal URL, whose host has no domain and is unreachable from outside Render),
#    AUTH_TOKEN_SECRET = the API service's generated value (dashboard → API → Environment).
#    Replace the postgresql:// prefix with postgresql+psycopg2:// (SQLAlchemy 2.1 maps plain
#    postgresql:// to psycopg v3, which is not installed). scripts/start_api.sh does this on Render.
export DATABASE_URL='<external database url>' AUTH_TOKEN_SECRET='<value>'
export STAFF_A_TOKEN=$(python -m api.auth issue-token --user-id demo-staff-a --ttl-hours 1)
export STAFF_B_TOKEN=$(python -m api.auth issue-token --user-id demo-admin-b --ttl-hours 1)

# 3. Flagged intake -> clinic "default" review queue; clinic B denied
python -m scripts.hosted_check --api "$API"
#    Every line must be [PASS]; it prints the intake id and the expected Idempotency-Key.

# 4. Signed webhook (only when WEBHOOK_URL is set to a receiver you control; on the public demo it is unset,
#    so expect no webhook_delivery event and see §9.1 instead): at the receiver, find the request with Idempotency-Key intake.escalated:<id>,
#    save its raw body byte-for-byte to body.json and copy X-Webhook-Signature.
WEBHOOK_SECRET='<API WEBHOOK_SECRET value>' \
  python -m scripts.verify_webhook --body-file body.json --signature 'sha256=...'
#    Expect: VALID signature | event=intake.escalated intake_id=<id> clinic_id=default
```

Optionally, open the frontend URL, submit a synthetic intake such as *"Synthetic test: crushing chest pain and trouble breathing"*, then open `/staff`, paste the `demo-staff-a` token and confirm the intake is in the `default` clinic's queue.

The same flow (`scripts/hosted_check.py` + `scripts/verify_webhook.py`) runs in CI in-process against SQLite and a loopback receiver (`tests/test_deploy_demo.py`), and the migrate-then-seed sequence runs against PostgreSQL (`tests/test_persistence_postgres.py`). That establishes readiness only; **hosted acceptance is verified only when §6 has been run against the deployed services.**

## 9. Public demo safety and lifecycle (Issue #67)

The hosted demo is meant to be shared with anonymous visitors, who will click every scenario. This section keeps it safe to click, explains its own delays, and keeps it online when the link is shared. Configuration and frontend only: no backend code, API, auth, RBAC or clinic-isolation change.

### 9.1 Webhook isolation

**Decision: `WEBHOOK_URL` is unset on the hosted API** (changed in the dashboard on 2026-10-14). `WEBHOOK_SECRET` stays as generated.

Why unset rather than a controlled receiver: it needs no second service, account or secret, has no side effects by construction, and costs nothing. A receiver would only matter for demonstrating delivery, which CI already covers end to end (`tests/test_deploy_demo.py`, loopback receiver) and the Phase 6 hosted acceptance recorded on 2026-10-09 (§7).

Behaviour (`api/webhook.py`, `_config()`): delivery runs only when both `WEBHOOK_URL` and a `WEBHOOK_SECRET` of ≥ 32 characters are set. With the URL unset, `notify_escalation` returns `disabled` before any network call, writes no `webhook_deliveries` row and logs one warning per newly stored intake:

```
Escalation webhook disabled: WEBHOOK_URL and WEBHOOK_SECRET (>= 32 chars) are both required
```

Intake, escalation (`needs_review`), the review queue, auth and clinic isolation are unaffected; this exact configuration is tested (`tests/test_webhook.py::test_missing_or_invalid_config_disables_webhook_safely`, case `(None, SECRET)`).

How `disabled` appears: there is no `webhook_delivery` event in the intake's evidence timeline (the timeline lists only delivery rows), and the warning above is in the API logs at the intake's time. Older intakes keep their historical delivery rows (e.g. the Phase 6 acceptance intake).

Dashboard steps (account owner):

1. Dashboard → `healthcare-ai-api` → *Environment*.
2. Delete the `WEBHOOK_URL` row entirely (do not leave an empty value). Keep `WEBHOOK_SECRET`.
3. *Save and deploy*. A redeploy is required because settings are read once at process start; no rebuild is needed (runtime variable). Leave the frontend unchanged.
4. Optionally delete the old receiver URL at its provider.

Verify before any flagged submission:

1. *Environment* no longer lists `WEBHOOK_URL`; the deploy is *Live*; `GET /health` → 200, `llm_mode: mock`.
2. Submit one **non-flagged** synthetic intake with unique text (a routine intake is never escalated, so it cannot send a webhook under either configuration). The notifier still checks its configuration for every newly stored intake, so the API logs must show the warning above at that time. Only then submit flagged presets.
3. After a flagged submission, its timeline must have no `webhook_delivery` event, and the logs show the warning again.

`render.yaml` still declares `WEBHOOK_URL` with `sync: false` (a Blueprint sync does not set a value for it); when creating a new Blueprint, leave it empty.

### 9.2 Cold start

Every page (`/`, `/intake`, `/staff`, `/system-card`) runs a bounded wake check on the existing `GET /health` (`app/components/ApiStatus.tsx`, `waitForApi` in `app/services/api.ts`): up to 6 attempts, each with a 15 s timeout, started at most once every 15 s (at least 3 s after a timed-out attempt), so the window is about 75–105 s even when attempts fail instantly. A fast answer shows nothing. If the first check is slow (> 1.5 s) or fails, the page shows *"Waking the demo server (can take up to a minute)"* with the attempt count, then *"Demo server is awake"*. If every attempt fails, it shows an actionable error (checked for over a minute; still starting, redeploying or offline; try again in a minute or contact the person who shared the demo) with a *Try again* button. The landing page starts the check too, so the server wakes while the visitor reads. Tests: `app/tests/ApiStatus.test.tsx`.

### 9.3 Staff access policy

Staff tokens are **issued on request by the demo operator** (§6 step 2, short TTL) and are **never published**: not on the site, in the repository, in screenshots or in the browser bundle. There is no public token endpoint, guest login or shared password, and none will be added for the demo. The landing page's Staff entry and the `/staff` sign-in page say this to visitors and point them to the patient intake and system card, which need no token.

### 9.4 Demo-data lifecycle runbook

| Item | Value |
| --- | --- |
| Database | `healthcare-ai-db`, Render free PostgreSQL (PostgreSQL 18) |
| Created | on or before 2026-10-09 (first deploy, §7) |
| Expires | **no later than 2026-11-08** (30 days after creation on the free plan); confirm the exact date on the dashboard |
| Data | migrations + synthetic seed only (`db.seed_demo`); visitor intakes are synthetic and disposable |

**Check expiry** (before sharing the link, and weekly while it is shared): Dashboard → `healthcare-ai-db` → *Info*. Render shows the expiration date and a warning banner as it approaches, and emails the account owner. Record the exact date in the table above when it is first confirmed. Free-plan terms (expiry period, any grace period before deletion) can change: check render.com/docs/free before relying on them.

**Recreate after expiry** (data is lost; the demo has nothing to keep):

1. Dashboard → `healthcare-ai-db` → *Settings* → *Delete Database* (a workspace can have only one free database).
2. Dashboard → *Blueprints* → this Blueprint → *Manual sync*. Render recreates `healthcare-ai-db` from `render.yaml` (same `databaseName` and `user`) and relinks the API's `DATABASE_URL` (`fromDatabase`). If the sync does not recreate it, create a free PostgreSQL named `healthcare-ai-db` (database `healthcare_ai`, user `healthcare_ai`) and set the API's `DATABASE_URL` to its *Internal Database URL*.
3. `healthcare-ai-api` → *Manual Deploy* → *Deploy latest commit*. `scripts/start_api.sh` applies every migration and runs the seed.
4. Logs: `Migrations complete (N applied)` with N = all migration files, `Demo seed complete (… rows created)`, `Application startup complete`.
5. Update the *Created* / *Expires* rows above and run the live-link check.

**Re-seed only** (database still valid, seed rows missing or changed): *Manual Deploy* (or *Restart*) of the API runs `python -m db.seed_demo` again; it inserts missing rows with fixed ids and never changes existing ones. From a checkout: `APP_ENV=demo DATABASE_URL='<external url, postgresql+psycopg2://…>' python -m db.seed_demo` (it refuses to run unless `APP_ENV=demo`). It does not reset seeded intakes whose status staff changed; to restore exactly, recreate the database.

`AUTH_TOKEN_SECRET` and `WEBHOOK_SECRET` live on the API service, not in the database, so recreating the database does not change them; tokens are re-issued as in §6 step 2.

**Live-link check before sharing** (no token needed, read-only; wakes the services first):

```sh
API=https://healthcare-ai-api-tovn.onrender.com
WEB=https://healthcare-ai-frontend-1s23.onrender.com
curl -fsS -m 120 "$API/health"                     # {"status":"ok", ... "llm_mode":"mock"}
curl -fsS -m 60 -o /dev/null -w '%{http_code}\n' "$API/api/system-card"
for p in / /intake /staff /system-card; do curl -fsS -m 120 -o /dev/null -w "$p %{http_code}\n" "$WEB$p"; done
```

Expect 200 everywhere. Then, with an operator-issued `demo-staff-a` token, confirm the `default` queue lists `demo-intake-a1`–`a4` (a missing seed means the database was recreated without a deploy), and confirm in the dashboard that `WEBHOOK_URL` is still unset (§9.1) and the database expiry is after the period the link will be shared.

Options not taken (billing decisions for the account owner, #67 out of scope): a paid database removes the expiry; paid instances remove cold starts; rate limiting the public intake endpoint.
