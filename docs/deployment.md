## 1. Platform choice: Render (Blueprint)

One file, [`render.yaml`](../render.yaml), declares the whole environment:

| Resource | Render type | Built from |
| --- | --- | --- |
| `healthcare-ai-api` | Web service, Docker | `Dockerfile` (FastAPI) |
| `healthcare-ai-frontend` | Web service, Docker | `app/Dockerfile` (Next.js standalone) |
| `healthcare-ai-db` | Managed PostgreSQL | — |

Why Render:

* Runs the two existing Dockerfiles unchanged and provides managed PostgreSQL, so the stack matches `docker-compose.yml` without new infrastructure.
* One declarative file instead of Terraform/AWS (roadmap §8): no VPC, IAM or load balancer to manage.
* Built-in HTTPS, health checks, generated secrets (`generateValue`) and dashboard-managed secrets (`sync: false`).
* A free tier is enough for a demo (see §5).

Redis from `docker-compose.yml` is not deployed: nothing in the application uses it.

## 2. What happens on deploy

The API's start command (`dockerCommand: sh scripts/start_api.sh` in `render.yaml`):

```sh
set -e
python -m db.migrate
python -m db.seed_demo
exec uvicorn api.main:app --host 0.0.0.0 --port "${PORT:-8000}"
```

1. **Migrations** (`db/migrate.py`) apply pending files from `db/migrations/`; applied files are recorded in `schema_migrations`, so this is safe on every start.
2. **Demo seed** (`db/seed_demo.py`) inserts any missing synthetic demo rows (below) and never changes existing ones.
3. **Server** starts only if both steps succeed. Render's health check (`GET /health`, which also reports `llm_mode`) only passes once the server is up, so a failed migration leaves the deploy unhealthy instead of serving an unmigrated database.

The migrations run in the start command rather than a pre-deploy command because Render's pre-deploy commands are not available on the free instance type.

The frontend health check is `GET /`.

### Synthetic demo seed

| User id | Email | Clinic | Role |

## 3. Environment variables

**API** (`healthcare-ai-api`):

| Variable | Source | Notes |
| --- | --- | --- |
| `DATABASE_URL` | From `healthcare-ai-db` | Internal connection string. |
| `LLM_MODE` | `mock` in `render.yaml` | Real mode requires explicitly setting `LLM_MODE=real` **and** `OPENAI_API_KEY` in the dashboard; startup fails if the key is missing (#22). Not recommended for the public demo. |
| `AUTH_TOKEN_SECRET` | Generated by Render | Signs staff tokens. Needed locally to issue tokens (§6). |
| `WEBHOOK_SECRET` | Generated by Render | Signs webhook payloads. Needed by the receiver to verify signatures. |
| `WEBHOOK_URL` | Entered at creation (`sync: false`) | HTTPS receiver URL. The payload carries only ids ([`escalation_webhook.md`](escalation_webhook.md)). |
| `CORS_ALLOWED_ORIGINS` | Entered at creation | The frontend's public origin exactly as shown on its service page, e.g. `https://healthcare-ai-frontend-1s23.onrender.com`. |
| `APP_ENV` | `demo` | Shown by `/health`. |

**Frontend** (`healthcare-ai-frontend`):

| Variable | Source | Notes |
| --- | --- | --- |
| `NEXT_PUBLIC_API_BASE_URL` | Entered at creation | The API's public URL. Inlined into the browser bundle at **build** time; it is the only frontend variable and is never a secret. Changing it requires a rebuild. |
| `PORT` | `3000` | Next.js standalone server port. |

No secret has a value in the repository. `tests/test_deploy_demo.py` fails if a secret-like key in `render.yaml` has a literal value, if the frontend service receives anything other than `PORT` and `NEXT_PUBLIC_API_BASE_URL`, or if the UI reads any other `process.env` variable.

## 4. Deployment steps (requires the account owner)

1. **Receiver.** Create a webhook receiver URL that shows the raw request body and headers, e.g. a free [webhook.site](https://webhook.site) URL, or any HTTPS endpoint you control. The payload has no PHI.
2. **Render account.** Sign in to Render and connect the GitHub repository.
3. **Blueprint.** Dashboard → *New* → *Blueprint* → select this repository, branch `main`. Render reads `render.yaml` and asks for the `sync: false` values:
   * `WEBHOOK_URL` = receiver URL from step 1
   * `CORS_ALLOWED_ORIGINS` = the frontend's public URL
   * `NEXT_PUBLIC_API_BASE_URL` = the API's public URL

   The public hostnames are not known until the services exist: when `<service-name>.onrender.com` is already taken, Render adds a random suffix (this deployment got `healthcare-ai-api-tovn` and `healthcare-ai-frontend-1s23`; the unsuffixed names belong to another account). Enter placeholders if needed, then after creation **copy** each URL from the service page (do not retype it; `l`/`1`/`t` are easy to confuse) and set:
   * API → `CORS_ALLOWED_ORIGINS` → *Save and deploy*;
   * Frontend → `NEXT_PUBLIC_API_BASE_URL` → **Save, rebuild, and deploy**. A plain *Save and deploy* does not rebuild the image, so the browser bundle keeps the old API URL.
4. **Apply.** Confirm the Blueprint with the free plans. `autoDeployTrigger` is `off`, so later deploys are manual (*Manual Deploy* in the dashboard).
5. **Check the API logs** for `Migrations complete` and `Demo seed complete`, and that the service shows as healthy.

## 5. Costs and limitations

All three resources are on Render's **free** plans in `render.yaml` (no payment method should be needed for this configuration; confirm current terms at render.com/pricing before applying). Known free-tier limits, as documented by Render at the time of writing:

* Free web services spin down after ~15 minutes without traffic; the next request waits for a cold start (up to about a minute).
* A free PostgreSQL database expires after a fixed period (30 days at the time of writing) unless upgraded; data is lost. Only one free database per workspace.
* The container filesystem is ephemeral: the JSONL audit file (`audit.jsonl`) is lost on restart. Audit events are also printed to stdout and visible in Render's logs.
* Single instance, single environment, no autoscaling, no backups on the free database.

Upgrading to paid instance types (roughly a few US dollars per month per service and database) removes the spin-down and expiry; that is a billing decision for the account owner and is not part of this issue.

Other limitations: one webhook receiver for all clinics; tokens are issued by an operator CLI (no login UI); no rate limiting on the public intake endpoint (roadmap §7).

## 6. Hosted verification (exit-criterion flow)

Run from a local checkout with dependencies installed. Values come from the Render dashboard.

```sh
API=https://healthcare-ai-api-tovn.onrender.com   # this deployment; copy yours from the API service page

# 1. Health and mode
curl -fsS "$API/health"          # expect {"status":"ok", ..., "llm_mode":"mock"}

# 2. Issue staff tokens locally against the hosted database.
#    DATABASE_URL = healthcare-ai-db "External Database URL" (dashboard → database → Connect;
#    not the Internal URL, whose host has no domain and is unreachable from outside Render),
#    AUTH_TOKEN_SECRET = the API service's generated value (dashboard → API → Environment).
#    Replace the postgresql:// prefix with postgresql+psycopg2:// (SQLAlchemy 2.1 maps plain
#    postgresql:// to psycopg v3, which is not installed). scripts/start_api.sh does this on Render.
export DATABASE_URL='<external database url>' AUTH_TOKEN_SECRET='<value>'
export STAFF_A_TOKEN=$(python -m api.auth issue-token --user-id demo-staff-a --ttl-hours 1)
export STAFF_B_TOKEN=$(python -m api.auth issue-token --user-id demo-admin-b --ttl-hours 1)

# 3. Flagged intake -> clinic "default" review queue; clinic B denied
python -m scripts.hosted_check --api "$API"
#    Every line must be [PASS]; it prints the intake id and the expected Idempotency-Key.

# 4. Signed webhook: at the receiver, find the request with Idempotency-Key intake.escalated:<id>,
#    save its raw body byte-for-byte to body.json and copy X-Webhook-Signature.
WEBHOOK_SECRET='<API WEBHOOK_SECRET value>' \
  python -m scripts.verify_webhook --body-file body.json --signature 'sha256=...'
#    Expect: VALID signature | event=intake.escalated intake_id=<id> clinic_id=default
```

Optionally, open the frontend URL, submit a synthetic intake such as *"Synthetic test: crushing chest pain and trouble breathing"*, then open `/staff`, paste the `demo-staff-a` token and confirm the intake is in the `default` clinic's queue.

The same flow (`scripts/hosted_check.py` + `scripts/verify_webhook.py`) runs in CI in-process against SQLite and a loopback receiver (`tests/test_deploy_demo.py`), and the migrate-then-seed sequence runs against PostgreSQL (`tests/test_persistence_postgres.py`). That establishes readiness only; **hosted acceptance is verified only when §6 has been run against the deployed services.**

## 7. Hosted verification result (2026-10-09)

Run against the URLs above from `main` at `3e984e3`, following §6:

* `/health` 200 with `llm_mode: mock`; frontend `/` and `/staff` 200; CORS preflight from the frontend origin allowed.
* API logs: `Migrations complete (3 applied)` and `Demo seed complete (7 rows created)` on first deploy; `0 applied` / `0 rows created` on later deploys.
* `scripts/hosted_check.py`: all 8 checks `[PASS]` — flagged synthetic intake (`emergency_signal`) stored as `needs_review` in clinic `default`, present in `demo-staff-a`'s queue, **403** for `demo-admin-b`, absent from `demo-clinic-b`'s queue.
* Receiver: exactly one POST with `Idempotency-Key: intake.escalated:<intake id>`; `scripts/verify_webhook.py` → `VALID signature`, a tampered signature is rejected; `webhook_deliveries` row `delivered`, 1 attempt, HTTP 200.
* Payload limited to `event`, `schema_version`, `idempotency_key`, `intake_id`, `clinic_id`. API logs contain no intake text and no tracebacks. The browser bundle contains only the API URL and no secret names.
